# Лаборатори №3 — Чанарын сценарио → SLO → k6 threshold

## Оюутны мэдээлэл ба орчин

- Оюутны нэр: **Ундрах**
- Оюутны код: **b252270135**
- Node.js: `v18.20.8`
- k6: `v2.3.0 (commit/e088784614, go1.26.8, darwin/arm64)`
- API: `http://localhost:3000`

## Ажиллуулах

```sh
npm install
node server.js
```

Өөр терминалд:

```sh
k6 run slo-test.js
```

Сервер нь `POST /cart/add`-д хурдан `201`, `GET /report`-д 200–400 мс санамсаргүй саатлын дараа `200`, `POST /pay`-ийн ойролцоогоор 5%-д `500` буцаана. Энэ нь туршилтын зориулалттай локал API юм.

## Чанарын сценарио

### 1. Гүйцэтгэл — `POST /cart/add`

1. **Тойм:** Сагсанд бараа нэмэх үйлдэл хэвийн ачаалалд хурдан дуусах ёстой.
2. **Системийн төлөв:** Локал API ажиллаж, `/cart/add` endpoint хүсэлт хүлээн авах боломжтой.
3. **Орчны төлөв:** 20 виртуал хэрэглэгч (VU), нэг минутын турш HTTP хүсэлтүүдийг давтан илгээнэ.
4. **Гадаад өдөөлт:** Хэрэглэгч барааны мэдээлэлтэй `POST /cart/add` хүсэлт илгээнэ.
5. **Шаардлагатай хариу:** API `201` амжилтын хариуг буцаана.
6. **Хэмжүүр:** `http_req_duration{name:cart}`-ийн p95 нь 200 мс-ээс бага байна.

### 2. Найдвартай байдал — `POST /pay`

1. **Тойм:** Төлбөрийн хүсэлтийн алдааны хувь зөвшөөрөгдөх түвшнээс хэтрэхгүй байх ёстой.
2. **Системийн төлөв:** API төлбөрийн хүсэлт хүлээн авч, зориудаар ойролцоогоор 5%-д `500` гаргана.
3. **Орчны төлөв:** 20 VU нэг минутын турш сагсны болон төлбөрийн хүсэлт давтан илгээнэ.
4. **Гадаад өдөөлт:** Хэрэглэгч `POST /pay`-аар төлбөр хийх хүсэлт илгээнэ.
5. **Шаардлагатай хариу:** Амжилттай хүсэлт `200`; нийт төлбөрийн хүсэлтийн алдаа 8%-аас бага байна.
6. **Хэмжүүр:** `http_req_failed{name:pay}`-ийн rate 0.08-аас бага байна.

### 3. Хүртээмж — бүх endpoint

1. **Тойм:** Серверийн түр зогсолт болон сэргэлтийн үед хүсэлтүүдийн амжилтын хувь SLO-г хангах ёстой.
2. **Системийн төлөв:** `/cart/add`, `/pay`, `/report` endpoint-ууд нэг локал серверт ажиллана.
3. **Орчны төлөв:** 20 VU хүсэлт явуулна; chaos туршилтаар серверийг зогсоогоод 10 секундийн дараа дахин асаана.
4. **Гадаад өдөөлт:** Бүх endpoint рүү хүсэлт үргэлжилж, серверийн зогсолт/сэргэлт тохиолдоно.
5. **Шаардлагатай хариу:** Нийт шалгалтын 90%-аас дээш нь амжилттай; API дахин асахад хүсэлтүүд амжилттай болж эхэлнэ.
6. **Хэмжүүр:** `checks`-ийн rate 0.90-ээс их байна. Нэг check нь нэг HTTP хариуны амжилтыг хэмжинэ.

## SLO хүснэгт

| Чанарын шинж | SLI | SLO босго | Цонх | k6 threshold |
|---|---|---:|---|---|
| Гүйцэтгэл | `/cart/add` HTTP хүсэлтийн p95 latency | `< 200 ms` | 1 минутын load run | `http_req_duration{name:cart}: p(95)<200` |
| Найдвартай байдал | `/pay` HTTP алдааны хувь | `< 8%` | 1 минутын load run | `http_req_failed{name:pay}: rate<0.08` |
| Хүртээмж | Бүх endpoint-ийн амжилттай check-ийн хувь | `> 90%` (зорилтот доод хязгаар 90%) | Нэг run; chaos-д 2 минут | `checks: rate>0.90` |

### Error budget ба босго сонголт

90%-ийн хүртээмжийн зорилго нь цонхонд бүртгэгдсэн бүх шалгалтын хамгийн ихдээ 10%-ийг амжилтгүй байж болохоор зөвшөөрнө. Иймээс error budget = нийт check × (1 − 0.90) = нийт check-ийн 10%. Хэвийн run-д 8,946 check-ийн 10% буюу 894.6 check-ийн budget байсан; 145 check бүтэлгүйтсэнээр дотор нь багтсан. Chaos run-д 24,168 check-ийн budget 2,416.8 check байхад 8,670 check бүтэлгүйтсэн тул ойролцоогоор 6,253-аар давж, budget дууссан. 20 VU, нэг минутын туршилт нь хэвийн ачааллыг хянах богино лабораторийн цонх юм. `/pay`-ийн зориудын 5%-ийн алдаа нь жишээ системийн fault injection бөгөөд 8%-ийн босго санамсаргүй хэлбэлзэлд зай үлдээж, илүү олон алдааг барих зориулалттай. `/cart/add`-ийн 200 мс p95 нь энэ шууд хариулах endpoint-ийн хурдан үйлдлийн зорилго. 90%-ийн хүртээмж нь богино chaos эвдрэлийг ажиглах сургалтын босго; үйлдвэрлэлийн зорилго гэж ойлгож болохгүй.

## Туршилтын гаралт

`results/pass.txt` нь 1 минутын хэвийн ачааллын гаралт, `results/chaos.txt` нь серверийг 10 секунд зогсоож дахин асаах үеийн 2 минутын гаралт, `results/fail.txt` нь зориуд боломжгүй `/report` latency threshold-ийн гаралт байна. Гаралтуудыг k6 v2.3.0 дээр бодитоор авсан.

### PASS run

`results/pass.txt`-д `cart` p95 **1.73 ms**, `/pay`-ийн алдааны хувь **4.72% (141/2,982)**, нийт check-ийн амжилт **98.37% (8,801/8,946)** гэж бүртгэгдсэн. Гурван threshold бүгд PASS болсон.

### Chaos run

`results/chaos.txt`-д **15,498 амжилттай / 24,168 нийт check = 64.12% availability** гэж гарсан. Бүтэлгүй check 8,670 буюу 35.87%; `/pay`-ийн алдаа **37.90% (3,054/8,056)** болсон. Error budget 2,416.8 check байхад 8,670 алдаа гарсан тул төсөв хэтэрсэн. k6 `checks` болон `/pay` threshold-ыг хоёуланг нь FAIL гэж тэмдэглэсэн. Нэг серверийн зогсолт `/pay`-ийн алдааны SLO болон бүх хүсэлтийн availability SLO-г зэрэг зөрчсөн.

### Зориудын FAIL run

`slo-test-fail.js` нь `/report`-ийн p95-ийг `<100 ms` гэж шаардана. `results/fail.txt`-д хэмжсэн p95 **391.81 ms** болж, threshold биелээгүй; k6-ийн бодит non-zero exit code **99**-ийг файлын төгсгөлд хадгалсан.

## 8 өгүүлбэртэй дүгнэлт

1. Локал API нь хурдан, сааталтай, зориудаар алдаа гаргадаг гурван endpoint-оор чанарын өөр өөр зан төлөвийг загварчилсан.
2. Хэвийн ачааллын run-д `/cart/add`-ийн p95 **1.73 ms** гарч, **200 ms** босгыг хангасан.
3. `/pay`-ийн алдаа **4.72%** байсан нь **8%** reliability босгоос доогуур байв.
4. Бүх check-ийн **98.37%** нь хэвийн үед амжилттай болж, availability босго давсан.
5. **90%** availability SLO нь нийт check-ийн **10%**-тай тэнцэх error budget олгоно.
6. Chaos run-д серверийг **10 секунд** зогсооход бодит availability **64.12%** болж буурав.
7. Энэ тасалдлын үед `/pay` алдаа **37.90%** хүрч, availability болон reliability threshold хоёулаа зөрчигдсөн.
8. `/report`-ийн p95 **391.81 ms** гарсан тул **100 ms** босго зориуд FAIL болж, k6 **99** кодоор гарсан.
